A page can pass every linter and still be unusable.

That is not a hypothetical. It is the default output of an AI builder. The markup is valid, the attributes a checker knows are present, and a blind visitor opens the page and hears a button with no name. Preflight exists for that gap: it reads the page the way a screen reader consumes it, then hands back an instruction a builder can act on.

## What the page says

Here is a real page, generated by an AI builder, scanned by Preflight. This is what a blind visitor hears:

```
  1  document
  2  image                        <- an image with no name
  3  link, Pricing
  4  button                       <- a button with no name
  5  heading, Ship your landing page in minutes, level 1
  6  image                        <- another one
```

Everything on that page is technically valid HTML. Every attribute a linter checks is either present or reported by axe. And a person using a screen reader cannot tell what those two images are or what that button does.

No attribute-based tool shows you this. Preflight does, because it reads the page the way it will actually be consumed.

The full sequence, from URL to repair prompt, is in [What happens during a Preflight scan](./how-preflight-works.html).

## Three layers

The transcript is the first layer. The page is walked with a screen reader and every phrase it speaks is recorded, in order. A role announced with no name is marked and explained in plain language. That is the observation no linter can produce. It is the experience.

The second layer is the verdict. One score that refuses to be green while someone is blocked. A page with 92 findings fixed and one unusable checkout does not get an A. `92/100 but checkout is broken` is how a tool gets uninstalled.

The third is the fix prompt. An ordered prompt, ready to paste into the tool that generated the page. Every step names the element, the change, and the announcement the reader must produce afterwards:

```markdown
## Step 2 - Elements must meet minimum color contrast ratio thresholds
Where: the section #pricing
Affects 2 elements that share this cause. Fix the shared source, not each element:
  - .hero > p
  - footer span
Do: Change the text or background colour. Measured: ratio 1.89:1 (needs 4.5:1),
    foreground #b9bcc4, background #ffffff.
Reader must announce: Re-run Preflight: the contrast rule reports no failing elements.
```

That last line is the difference between a suggestion and a contract. The builder can verify its own work instead of guessing "looks good to me".

## Why the transcript is the product

Most accessibility tooling answers a cheap question: does the markup declare the right things? It can be answered by parsing HTML, and parsing HTML scales. The expensive question is what a person actually hears when they use the component. That requires running the page, in a browser, with assistive technology attached, and reading the output.

The gap between those questions is where the worst bugs live. A live region can overwrite the native announcement and make the experience worse while every attribute stays correct. A tree can render a valid `role="tree"` with no name and pass an automated audit. A sortable header can announce "toggle button, not pressed" while the table is sorted just fine.

None of those are caught by a rule that asks whether an attribute is allowed. They are caught by listening.

## What it refuses to claim

A tool that overclaims is trusted once.

Preflight does not certify anything. Automated checks catch roughly a third of accessibility defects, and every report says so in the body.

The transcript is virtual. It reflects what the DOM declares, not how VoiceOver or NVDA times a specific announcement in a specific browser.

It does not crawl. One URL per scan, by design.

It does not fix your code. It measures, explains, and hands you the instruction. Editing the project is the builder's job, and keeping that boundary is why the MCP server can be called without an approval prompt.

A green score is not compliance. It means no detectable, blocking defect was found on that page at that moment.

## Measured, not asserted

The README reports a repair loop, not a demo. Three model families were given the Preflight prompt and their output was re-scanned by the same engine. 95.8% of findings closed, with zero regressions, and both editors preserved every image, link and word on the page. A live product was repaired from 49/100 F to 100/100 A, with every step verified by re-scanning the deployed URL.

That is the part I care about. A scan that produces a score is a thermometer. A scan that produces a repair the builder can execute, and then verifies the result, is a gate.

## How it fits the work

Preflight is open source and local-first. The CLI accepts `localhost` and private addresses by default, because the person running it and the machine being scanned are the same. A hosted server refuses private hosts, so a stranger's URL never reaches the network.

Exit codes are the point: `0` pass, `1` gate failed, `2` scan error. Drop it in CI and a pull request that ships an unusable button stops being merged.

It is built for the sites AI builders produce, where every attribute is present and the page is still unusable. It is also useful on any page where "we ran a linter" has been standing in for "a person can use this".

## The rule

Do not ask what the markup declares. Ask what the screen reader says when a person uses the page.

Those are different questions, and only one of them is the product.
